# Rule: Internationalisation (`src/libs/i18n/`)

Every user-facing string the API returns — response messages, error messages, field-error messages,
mail subjects, validation messages — is a **catalog key**, not an English literal.

## The two entry points

```ts
import { t } from "@i18n";

t("profile.retrieved");
t("settings.roles.nameExists", { name });
```

- `t(key, vars?)` resolves against the **current request locale**. Use it everywhere inside a request.
- `translate(key, vars?, locale?)` takes an explicit locale — for workers, scripts, startup logs.

`key` is typed `TranslationKey`, so an unregistered key is a **compile error**.

## Catalogs: two flat files, moved together

- `src/libs/i18n/locales/en.json` and `src/libs/i18n/locales/id.json`.
- **Flat** maps of dotted key to string — `"auth.invalidCredentials"`, `"settings.users.notFound"`.
  There is no nesting; the dots are part of the key. Groups: `common.`, `errors.`, `validation.`,
  `auth.`, `profile.`, `settings.users.`, `settings.roles.`, `settings.permissions.`,
  `settings.select.`, `datatable.`, `health.`, `mail.`. One blank line between groups.
- Interpolation is double-brace (`{{name}}`), filled from `vars`.
- `DEFAULT_LOCALE` is `en`, the fallback for an unsupported locale or a missing key.

**`en` and `id` move together**: a key added to one is added to the other in the same change.

## `keys.generated.ts` is generated

After touching either catalog run `bun run i18n:keys`, which rewrites
`src/libs/i18n/locales/keys.generated.ts`. Never hand-edit it. The pre-commit hook runs it too.

## Where the locale comes from

`src/libs/fastify/plugins/externals/i18n.plugin.ts` reads `Accept-Language` in `onRequest`, resolves
it with `parseAcceptLanguage`, stores it with `enterLocale`, and echoes `Content-Language` on the
response. `getCurrentLocale()` reads it back. Work that leaves the request (a queued mail) captures
`getCurrentLocale()` into the job payload; the worker wraps its work in `runWithLocale`.

## Validation messages

`translateValidationIssue` (`src/libs/i18n/validation.ts`) maps a Zod issue onto the `validation.*`
keys; the error plugin calls it for every validation failure. A new constraint it cannot classify gets
a `validation.*` key **and** a branch — raw Zod English never reaches the client.

## Don't

1. Don't put an English literal into a `ResponseToolkit` message, a thrown error, or a mail subject.
2. Don't hand-edit `keys.generated.ts`, and don't add a key to `en.json` only.
3. Don't translate log messages, error codes, constraint names, or the `field` names in `errors[]`.
4. **No `t()` in a repository.** Repositories return `null`; the service that throws owns the
   message ([services-crud.md](./services-crud.md)). The one exception is `DatatableToolkit`, whose
   400s for bad sort/filter input are raised from inside repository `findAll` calls.

# Security

How authentication, authorization, and request hardening work in `clean-fastify`. To report a
vulnerability, see [`.github/SECURITY.md`](../.github/SECURITY.md).

## Passwords

- Hashed with bcrypt (cost 10) through `Hash` in `@utils`; never stored or logged in plain text.
- New passwords (register, reset, admin reset, own change) must match `StrongPassword`: at least 8
  characters with upper case, lower case, a digit and a symbol.
- Response schemas never include the hash; repositories select explicit columns.

## Tokens

### Access and refresh JWTs

|             | Access                                       | Refresh                        |
| ----------- | -------------------------------------------- | ------------------------------ |
| Secret      | `JWT_SECRET`                                 | `JWT_REFRESH_SECRET`           |
| Lifetime    | 1 day                                        | 7 days                         |
| Payload     | `{ id, type: "access" }`                     | `{ id, type: "refresh", jti }` |
| Accepted by | `request.authenticate()` on protected routes | `POST /auth/refresh` only      |

- Both secrets are **required with no default**; the process will not boot without them. Use two
  different random values.
- `request.authenticate()` verifies with `JWT_SECRET` and requires `type: "access"`.
  `/auth/refresh` verifies with `JWT_REFRESH_SECRET` and requires `type: "refresh"`. A token of one
  kind is rejected by the other on both the signature and the claim.
- **Rotation.** Each issued refresh token's `jti` is stored in Redis (`refresh_token:<userId>`, 7 days).
  `/auth/refresh` accepts only the stored `jti`, then issues a new pair and stores the new `jti`, so a
  refresh token works once. A new login also replaces it, so one user has one live refresh token.
- `/auth/refresh` re-checks the user: a deleted or non-active user's refresh is refused and their
  stored `jti` dropped.
- There is no logout endpoint. Sessions end on password reset, own password change, and user
  deletion (see "Session invalidation").

### Verification and reset tokens

- Generated by `StrToolkit.random` from `crypto.getRandomValues` (100 characters for verification,
  255 for reset), stored in `email_verifications` / `password_reset_tokens` with a unique index.
- Expire after 1 hour (`verificationTokenLifetime()` / `resetPasswordLifetime()`, evaluated at issue
  time).
- **Single use**: consuming one stamps `used_at` on every unused token of that user, inside the same
  transaction as the write it authorises. A token that is unknown, expired, or used is a 400.
- **Revoke on issue**: issuing a new token stamps `used_at` on the user's earlier unused tokens, so
  only the newest link works.
- Mail is queued only after the transaction that created the token commits.

## Enumeration safety

- `POST /auth/login` compares the password first — against a fixed dummy bcrypt hash when the email
  is unknown, to keep timing equal — and answers an unknown email and a wrong password with the same 400. "Email not verified" and "account inactive" are only revealed after a correct password.
- `POST /auth/resend-verification` and `POST /auth/forgot-password` always return 200, whether the
  email is unknown, already verified, or eligible.
- `POST /auth/register` does reveal an existing live email (422); that is the accepted trade-off of a
  self-service register endpoint, and the rate limiter bounds it.

## Authentication on each request

`request.authenticate()` (`src/libs/fastify/plugins/app/auth.plugin.ts`) is called from the
module-level `onRequest` hook of every protected route file. It verifies the token, then loads
`UserInformation` (`{ id, name, email, roles, permissions }`) through `SessionService`: Redis first
(`user:<id>`, 1 hour), else the database, which returns a user only if `deleted_at IS NULL` and
`status = 'active'`. Anything else throws 401 and stops the request.

## Authorization (RBAC)

- Guards are route-level `onRequest` hooks from `@fastify-libs`:
  `PermissionGuard(["user list"])` requires every listed permission; `RoleGuard(["superuser"])`
  requires every listed role. Both throw `ForbiddenError` (403), so a refused request never reaches
  validation or the handler.
- `superuser` bypasses both guards.
- Permission strings are the 15 seeded `<group> <action>` names (`user`, `role`, `permission` x
  `list`, `create`, `detail`, `edit`, `delete`). A guard string the seeder does not produce fails
  closed (403 for everyone but superuser).
- Privilege-granting routes are role-gated, not permission-gated: `POST
/settings/users/:id/reset-password` and both `/settings/select-options/*` routes require
  `superuser`.
- There is no global default: an authenticated route without a guard is open to every logged-in user.
  Only `/profile` routes are deliberately unguarded (they act on the caller's own identity).

## Session invalidation

`SessionService` (`src/services/session.service.ts`) owns the cached identity and the refresh `jti`:

| Event                                                     | Effect                                                                     |
| --------------------------------------------------------- | -------------------------------------------------------------------------- |
| Admin updates a user (status, roles, email, name)         | that user's cached identity dropped                                        |
| Admin deletes a user                                      | identity and refresh `jti` dropped; the DB lookup refuses the deleted user |
| Admin or self-service password reset, own password change | identity and refresh `jti` dropped                                         |
| Role updated or deleted                                   | identity dropped for every holder of the role                              |
| Permission updated or deleted                             | identity dropped for every user holding it through a role                  |
| Profile updated                                           | identity reloaded                                                          |

So a suspended, blocked, or deleted user loses access on their next request, and permission changes
apply immediately. An access token issued before a password change stays valid until it expires (at
most 1 day) as long as the user stays active.

## Soft delete and uniqueness

Users are soft-deleted (`deleted_at`); every user read filters it. Live emails are unique: the service
checks first (422) and a partial unique index `users_email_unique_live` backs it in the database. A
deleted user's email can be registered again.

## Input validation

- Every body, params and querystring is a Zod schema; failures are 422 before the handler runs.
- `:id` params must be UUIDs.
- List `sort` and `sortDirection` are closed enums; filter keys and enum values are checked against
  the repository's allow-list (400). Nothing sorts or filters on a raw client string, and every query
  is parameterised by Drizzle.
- Request bodies are capped at 100 KB (`bodyLimit` in `src/app.ts`); larger bodies get 413.

## Rate limiting

`@fastify/rate-limit`, global, 100 requests per minute per client, stored in Redis so every API
process shares the count. The key is `request.ip` (the socket address); `X-Forwarded-For` and similar
client-supplied headers are never trusted, because rotating them would bypass the limit. Behind a
reverse proxy, configure Fastify's `trustProxy` for that proxy. Exceeding the limit returns 429 with
`x-ratelimit-*` and `retry-after` headers.

## CORS

`ALLOWED_HOST` is a comma-separated list of allowed origins; empty allows every origin (development
only). Methods `GET, POST, PATCH, DELETE`; headers `Content-Type, Authorization, Accept-Language`;
credentials disabled.

## Security headers

`@fastify/helmet` sets a restrictive CSP (`default-src 'self'`, no frames, no objects,
`frame-ancestors 'none'`), HSTS for one year with subdomains and preload, `nosniff`, a
`strict-origin-when-cross-origin` referrer policy, and hides `X-Powered-By`.

## API docs gate

`/docs` and `/docs/openapi.json` are registered only when `ENABLE_API_DOCS=true`. The flag defaults
to `false` and does not depend on `NODE_ENV`, so a deployment that forgets it stays closed.

## Operational notes

- Never commit `.env`; the `.env.example` JWT secrets are placeholders, and startup rejects them, any
  secret shorter than 32 characters, and identical access and refresh secrets.
- Logs go to stdout and `storage/logs/app.log`. Mail logs carry the template, locale and job id,
  never the recipient address; SMTP failures log only the error and response codes, because SMTP
  error text can quote the address.
- Redis holds the identity cache, refresh ids, rate-limit counters and the mail queue — protect it
  with `REDIS_PASSWORD` and keep it off public networks.
- The seeders create `superuser@example.com` and `admin@example.com` with a published password;
  remove or change them before exposing an environment.
- `bun run db:drop` / `make fresh` refuse to run with `NODE_ENV=production`.
